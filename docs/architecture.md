# 架构与职责

第一层由信息系统驱动，负责厂级设备与工位协调。第二层持有工位业务状态、传感器融合、
工件和工艺数据、多机器人协同、控制权切换。第三层为每种机器人提供符合统一接口的控制器，
封装厂商协议、标定、运动学、限位、轨迹执行、实时控制和故障行为。

本仓库是第二层的依赖和调试工具集。独立运行遥操是工具使用方式，不意味着本仓库成为工位系统。
不在这里放置某条产线的动作流程、设备地址硬编码、型号分支或电机参数。

| 能力 | 所属位置 |
| --- | --- |
| SpaceMouse 输入映射、通用客户端、记录与检查 | 本仓库 |
| 接料、焊接、抓取顺序和现场传感器业务逻辑 | 第二层应用 |
| 多机器人任务互锁、控制生产者租约和权限 | 第二层应用 |
| CAN / TCP 厂商 SDK、使能、反馈、IK、实时闭环 | 第三层控制器 |
| 接口规范及新控制器验收方法 | 本仓库 |

工具与控制器通过标准 ROS 2 消息解耦。HTTP API 提供状态发现和非硬实时控制，
客户端无需知道关节数量；控制器通过 `joint_names`、限位和能力描述自己。
高频输入推荐 ROS 2 或控制器持续 WebSocket；首版 HTTP 客户端逐请求连接，不用于硬实时流。

每台机器人使用独立 namespace，每个输入设备使用独立源 topic。同一个 SpaceMouse 默认只控制一个目标。
双臂协同应由工位系统明确实现，不能把一个速度流广播给多台机器人。

工位应在启动遥操前停止原实时指令生产者，结束遥操后再交回自动程序。
首版会检测同一速度 topic 的多个发布者并抑制输出，但 ROS 图发现存在延迟，不能作为互斥锁；
它也看不到 HTTP、WebSocket、其他运动 topic 或控制器之外的生产者。
生产部署的跨通道控制权仲裁应由工位或第三层明确实现。

通用能力按有实际使用方的需求逐步添加。推荐下一阶段依次完善控制器能力发现、
跨通道控制租约、统一状态录制与回放；工艺任务始终保留在应用仓库。
